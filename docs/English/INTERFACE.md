# Interfacing with SerialHex

[← Back to the README](../../README.md)

This document is for those who **maintain SerialHex** or who want to **connect another application** to it (for example an Electron / React interface). It describes what SerialHex exposes and what must stay stable.

A practical guide on the React application side can be placed in the repository of the application that uses the package (`docs/SERIALHEX.md`).

| Repository | Contents |
|---|---|
| `GUI_PyCommSerial` | This project: SerialHex Python tool + npm package `serialhex` (`js/`) |
| client application | Electron / React application that uses the `serialhex` package |

## Principle

A React application **does not call Python at run time**. SerialHex exists in two implementations sharing the same contract:

```
                        ┌───────────── the contract ────────────┐
                        │  Msg_*.json   (format)                │
                        │  tests/vectors.json (expected frames) │
                        └──────────────┬────────────────────────┘
                 ┌─────────────────────┴─────────────────────┐
      Python: serialhex.py + core/               TypeScript: js/ (npm package "serialhex")
      standalone tool, open source               built into the Electron / React application
```

- The **same message files** work in both.
- The **same frames** are produced, guaranteed by `tests/vectors.json`.
- The application installs the `js/` package; it needs neither Python nor the Tkinter interface.

This avoids shipping a Python interpreter in the installer and an extra process to monitor.

## The four interface points

### 1. The message format

Defined in [MESSAGES.md](MESSAGES.md). This is the main interface: a customer or an application only sees these files.

Stable points:
- `Msg_<function>.json` file names, group deduced from the name;
- keys `name`, `frame` (or `request`, protocol message), `params`, `checksum`, `description`, `group`;
- existing parameter types and checksum algorithms: their encoding never changes.

### 2. The test vectors

`tests/vectors.json` lists, for each case, a message, values and the expected frame (or an expected error). `tests/protocol_vectors.json` does the same for the protocol engine: built frames, decoded frames (fields, checks, error messages, colours), CRC check values, invalid protocol files. They are **generated by Python** and **checked by both implementations**.

```bash
python tools/gen_test_vectors.py     # regenerates tests/vectors.json
python tools/gen_protocol_vectors.py # regenerates tests/protocol_vectors.json
python -m unittest discover tests    # checks Python
cd js && npm test                    # checks TypeScript
```

### 4. The Electron IPC protocol

Useful if the application wants to write its own preload or call the channels directly. Every call goes through `ipcRenderer.invoke` and answers:

```ts
{ ok: true, value: ... }  |  { ok: false, error: "readable message in French" }
```

| Channel | Arguments | Response |
|---|---|---|
| `serialhex:list` | — | `PortInfo[]` (`path`, `description`, `manufacturer`, `vendorId`, `productId`, `serialNumber`) |
| `serialhex:check` | `path` | `{ status: 'free' \| 'busy' \| 'missing' \| 'error', message }` |
| `serialhex:open` | `{ path, baudRate, dataBits?, parity?, stopBits?, flow? }` | — |
| `serialhex:reconfigure` | `{ baudRate?, dataBits?, parity?, stopBits?, flow? }` | — |
| `serialhex:close` | — | — |
| `serialhex:write` | `Uint8Array` | — (resolved once the bytes are sent) |
| `serialhex:signals` | `{ dtr?, rts? }` | — |
| `serialhex:read-messages` | — | `[{ fileName, content }]` of the `messagesDir` folder |
| `serialhex:read-protocols` | — | `[{ fileName, content }]` of the `*.json` of the `protocolsDir` folder |

Events sent by the main process to the window that opened the port:

| Channel | Payload |
|---|---|
| `serialhex:data` | `Uint8Array`, raw bytes received (splitting into frames is done on the renderer side) |
| `serialhex:closed` | `string`, reason for a closing that was **not requested** (cable pulled out, error) |

Main process behaviour:
- only one port open at a time; opening a new port closes the previous one;
- the port is closed if the window that opened it is destroyed;
- the renderer can only read the `messagesDir` and `protocolsDir` folders passed to `registerSerialHexIpc`.

## Request / response protocol

The **protocol engine** exists in both languages: `core/protocol/` and `js/src/core/protocol/` (same split into files) read the same file of `protocols/` (every option: [CONF_PROTOCOL.md](CONF_PROTOCOL.md)) and give the same results, checked by `tests/protocol_vectors.json`.

```ts
// main process: registerSerialHexIpc(ipcMain, { messagesDir, protocolsDir })
import { parseProtocol, QUERY, RESPONSE, protocolSegments } from 'serialhex';

const files = await window.serialhex.readProtocolFiles();          // [{ fileName, content }]
const modbus = files.find((f) => f.fileName === 'modbus_rtu.json')!;
const proto = parseProtocol(modbus.content, modbus.fileName);          // ProtocolError if invalid

const frame = proto.buildQuery(1, 0x03, Uint8Array.of(0, 0, 0, 2));  // Modbus: read 2 registers
await link.send(frame);

const d = proto.decode(rx, RESPONSE);
if (d.ok && d.error === 0) console.log(d.requestId, d.data?.raw);
const colors = protocolSegments(d);                                  // [start, length, 'hdr' | 'cmd' | 'crc' | 'err' | 'perr_ok' | 'perr_ko']
```

Multi-frame formats, ASCII encoding and texts (same keys as the Python file):

```ts
const mbus = parseProtocol(text, 'mbus.json');                       // // and /* */ comments accepted
mbus.variantNames(QUERY);                                            // ['Courte', 'Longue']
mbus.build(QUERY, new Uint8Array(), { request_id: 5, command_id: 0x5B }, 'Courte');   // 10 5B 05 60 16
const r = mbus.decode(rx, RESPONSE);                                 // r.variant: 'Accusé' | 'Longue'
r.fields.map((f) => [f.name, f.meaning, f.description]);             // "values" / "description" of the file
mbus.language = 'en';                                                // {"fr", "en"} texts in English
mbus.errorTexts();                                                   // {code: text} in the chosen language

const ascii = parseProtocol(text2, 'modbus_ascii.json');             // "encoding": ascii_hex
ascii.frameEnd;                                                      // Uint8Array [0x0D, 0x0A]: splits received frames
const dd = ascii.decode(rx2, RESPONSE);                              // dd.binary = binary frame, dd.encoded = bytes received
ascii.displaySegments(dd, protocolSegments(dd));                     // colours of the ASCII characters
```

The **command library** (`core/commands/`: `tx` / `rx` fields, units, factor / offset, choices, bits) only exists in Python so far. `Msg_*.json` files containing `"commands"` or `"errors"` are accepted by the TypeScript package (ignored, without error). Next step for the React GUI: port it to `js/src/core/commands.ts`, on the same principle of shared vectors.

### Evolving the protocol engine

1. Python: `core/protocol/`; TypeScript: `js/src/core/protocol/` (same files, same rules, same error messages).
2. Add test structures in `tools/gen_protocol_vectors.py`, then `python tools/gen_protocol_vectors.py`.
3. Run the tests on both sides.

## Evolving SerialHex

### Adding a parameter type or a checksum

1. Python: `encode_param` or `checksum` in `core/frames.py`, widget in `ui/params_panel.py`.
2. TypeScript: `encodeParam` or `checksum` in `js/src/core/frames.ts`, type in `js/src/core/types.ts`.
3. Add cases in `tools/gen_test_vectors.py`, then regenerate `tests/vectors.json`.
4. Run the tests on both sides.
5. Document it in [MESSAGES.md](MESSAGES.md).

### What must never change

- The encoding of an existing type or checksum: message files delivered to customers depend on it.
- The name and meaning of the JSON keys.
- The names of the IPC channels and the `{ ok, value | error }` shape.

For an incompatible change, create a new type or a new algorithm rather than changing the existing one.

### Package versions

`js/package.json` follows semantic versioning:

| Change | Version |
|---|---|
| Fix with no effect on the API | `0.1.0` → `0.1.1` |
| New type, checksum, hook, function | `0.1.0` → `0.2.0` |
| API changed or removed | `0.x` → `1.0.0` (then next major) |

Write down each version in the repository's release notes, so that the application knows whether it can update safely.

## Distributing the package

| Method | Command on the SerialHex side | On the application side |
|---|---|---|
| Local folder | `cd js && npm install && npm run build` | `npm install ../GUI_PyCommSerial/js` |
| Git submodule | — | `git submodule add <url-GUI_PyCommSerial> GUI_PyCommSerial` then `npm install ./GUI_PyCommSerial/js` |
| Archive | `cd js && npm pack` | `npm install ./serialhex-0.1.0.tgz` |
| npm registry | `cd js && npm publish` | `npm install serialhex` |

## Public messages and proprietary messages

The `GUI_PyCommSerial` repository is open source: `msgLibrary/` only contains examples or the commands intended for customers. Message files specific to an application (internal commands of a product) stay in the private repository of that application. As the format is identical, a specific file can be delivered to a customer without exposing the rest.
